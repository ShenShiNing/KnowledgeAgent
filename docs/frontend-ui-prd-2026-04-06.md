# Groundpath 前端 UI PRD（文字版实现稿）

最后更新：2026-04-06

本文是面向实现的前端 UI PRD，服务对象不是设计评审，而是后续负责落地页面的 AI 或前端工程师。

它与 `docs/ui-product-polish-plan-2026-04-06.md` 的关系如下：

- `ui-product-polish-plan` 负责说明为什么当前界面仍有 demo 感，以及改造顺序
- 本文负责把“应该做成什么样”写成可执行规格，尽量减少实现时的自由发挥

本文默认不改 API 语义，不新增页面路由，不改变现有核心业务流程，只重构运行时视觉系统、页面结构与信息呈现方式。

## 1. 项目背景

### 1.1 产品定位

Groundpath / 溯知 是一个“可追溯 AI 知识工作台”，不是通用聊天壳子。

核心价值必须始终围绕三件事展开：

- 可检索：知识库、文档、结构化索引、范围过滤、回收站与版本管理
- 可对话：聊天、流式响应、工具调用、引用跳转、知识库作用域切换
- 可验证：来源片段、引用回查、文档详情、版本恢复、结构化 RAG 观测

### 1.2 本次 UI 改造目标

本次 UI 改造不是“做得更花”，而是把产品收敛成一个简洁、可信、质感强、信息秩序明确的知识工作台。

目标关键词：

- 简洁
- 可信
- 克制
- 有结构
- 有信息密度
- 精致但不浮夸

反目标：

- 不做潮流化玻璃拟态堆叠
- 不做大面积高饱和颜色铺底
- 不做炫技动效
- 不做“营销页一套、控制台一套、聊天页再一套”的割裂体验

## 3. 设计原则

### 3.1 One Product, One Shell

首页、认证页、工作台、聊天页、知识库页必须看起来属于同一个产品。允许功能氛围不同，但不允许颜色、圆角、层次、标题气质完全变成另一套语言。

### 3.2 结构先于装饰

质感主要来自：

- 稳定的版心
- 清晰的 surface 分层
- 强化后的标题与数字层级
- 有节奏的留白
- 克制但准确的品牌色使用

不是来自：

- 夸张阴影
- 无意义的模糊
- 大面积渐变字
- 高频动画

### 3.3 品牌色只出现在高价值位置

品牌绿不是页面底色，而是“准星”。

优先用于：

- 主按钮
- 当前活跃导航
- 关键图标底
- 重点状态标签
- Hero 内的高价值锚点

不用于：

- 大面积表格底色
- 所有卡片 hover 背景
- 全页背景铺色
- 所有图标都统一变绿

### 3.4 信息密度高，但阅读压力低

后台类页面允许信息密度高，但必须保证：

- 视线先看到主任务
- 再看到当前状态
- 最后看到次级对象和操作

严禁“信息很多但没有阅读路径”。

## 4. 视觉系统

### 4.1 设计方向

本项目最终视觉方向为三者混合，不可只取其一：

1. `Swiss Modernism 2.0`
   作用：建立理性的网格、标题秩序和专业感
2. `Dimensional Layering`
   作用：通过浅层阴影、边框和 surface 制造质感，但不厚重
3. `Trust & Authority`
   作用：首页和关键模块要能传递“可信知识系统”，而非玩具化 AI

结论：

- 登录后工作台以“瑞士式秩序 + 克制层次”为主
- 首页以“产品预览 + 信任锚点 + 能力证明”为主
- 整体保留品牌绿，但不走蓝色企业模板，也不走黑金奢侈风

### 4.2 字体策略

本项目优先沿用已有运行时字体体系，避免无必要的大规模字体切换：

- 主字体：`Manrope`
- 中文回退：`Noto Sans SC`
- 代码/模型名/技术标签：保留系统 `font-mono`

字体使用规则：

- Hero 主标题：`font-display`，字重 `700-800`，紧字距
- 页面标题：`font-display`，字重 `600-700`
- 普通正文：`font-sans`，字重 `400-500`
- 次级说明：降低字号和对比，而不是降低太多字重
- 模型名、版本号、快捷键：`font-mono`

禁止事项：

- 不引入花哨 serif 作为运行时主标题字体
- 不使用纯 monospace 充当产品标题

### 4.4 背景与质感

允许背景存在气氛，但必须轻：

- 浅色模式：以 `neutral-50` 为主体，在顶部或侧边加极浅绿色 radial glow
- 深色模式：允许深绿黑渐变，但不做纯黑
- 内容卡仍以清晰 surface 为主，不允许背景装饰影响文本对比

推荐原则：

- 装饰性渐变只存在于页面背景层和 Hero 层
- 表格、表单、聊天区的可读性优先于氛围感

### 4.5 阴影、边框、圆角

基础规则：

- 页面级大面板：`24px` 圆角
- 普通内容卡：`20px`
- 按钮 / 输入框：`14px-18px`
- 小标签 / pills：`999px`

阴影分级：

- `shadow-1`：极浅，用于默认卡片
- `shadow-2`：悬浮卡、Hero 面板
- `shadow-3`：对话框、抽屉

实现要求：

- 浅色阴影偏冷灰绿，不用纯黑
- 深色模式主要靠边框和明暗差，不靠重阴影

### 4.6 图标

统一使用 `Lucide`，不得混用 emoji、彩色插画风图标、粗细不一的其他套件。

图标规则：

- 导航图标：`16-18px`
- 操作按钮图标：`16px`
- 数据卡图标：`18-20px`
- Hero / 品牌图标底块：允许 `20-24px`

## 5. 布局系统

### 5.1 栅格与版心

公共站点：

- 主版心：`max-w-6xl`
- Hero 特殊内容：可放宽到 `max-w-7xl`

应用内：

- 页面内容画布最大宽度：`1280px`
- 常规左右 padding：桌面 `24px`，大屏 `32px`，移动 `16px`

### 5.2 登录后应用壳

应用壳必须成为产品识别锚点。

#### Desktop

- Sidebar 宽度：展开 `280px`，收起 `64px`
- Sidebar 与内容区之间有明确边界，但不是生硬灰线
- 内容区背景使用 `app-bg`
- 页面主滚动发生在内容区，而不是整个 body

#### Mobile

- 顶部出现移动端 header
- 侧边导航通过左侧 `Sheet` 打开
- 移动端内容区上下留白减少，但卡片圆角不降级为模板感矩形

### 5.3 标准页面骨架

登录后标准页统一采用三段式：

1. `Page Header`
   包含页面标题、返回或主操作、状态摘要
2. `Page Toolbar`
   包含搜索、筛选、视图切换、创建入口
3. `Page Content`
   包含列表、表格、卡片、空态、详情内容

所有支撑页默认遵循这个骨架，不再各写一套 header。

## 6. 核心组件规范

### 6.1 Button

必须提供四个稳定层级：

1. `Primary`
   背景 `brand-500`，hover `brand-600`，文字浅色
2. `Secondary`
   浅底描边，强调次要操作
3. `Ghost`
   用于工具栏、局部切换
4. `Destructive`
   删除、清空、永久操作

要求：

- 高度统一：`36 / 40 / 44`
- 不要出现过于圆润的气泡按钮泛滥
- hover 只做颜色与轻微 elevation，不做明显 scale

### 6.2 Surface Card

统一定义 5 类卡片，不允许业务页面随意拼：

1. `Hero Panel`
   用于首页首屏和大摘要
2. `Metric Card`
   用于统计值与状态指标
3. `Object Card`
   用于知识库、文档、功能入口
4. `Panel Card`
   用于表单、说明块、设置区
5. `Elevated Overlay`
   用于弹窗、抽屉、浮层

### 6.3 Nav Item

导航必须满足：

- 默认态低调
- hover 有明确背景反馈
- active 态有实心高亮或深浅差，而不是只改文字颜色
- 收起侧栏时，图标仍保持视觉中心

### 6.4 Input / Search / Select

输入组件统一策略：

- 背景清晰，不用过透的玻璃态
- focus ring 使用 `brand-300`
- 占位文案对比度不能过低
- 搜索框支持图标前缀
- 筛选区高度和按钮高度统一

### 6.5 Table

表格必须更像产品，而不是原始组件：

- 表头有弱背景分层
- 行 hover 有柔和高亮
- 操作列右对齐
- 数据为空时不留空白表格壳，而是切换为完整空态

### 6.6 Empty / No Results

所有空态必须包含三类信息：

1. 现在是什么状态
2. 为什么会这样
3. 下一步能做什么

禁止只写一句“暂无数据”。

### 6.7 Dialog / Sheet

对话框应表现为“高级面板”：

- 圆角更大
- 标题更强
- 描述区可读
- 危险操作按钮层级清晰

### 6.8 Chat Composer

聊天输入框属于产品识别点，必须单独打磨：

- 使用中性底 + 细边框 + 轻阴影
- 不允许继续使用写死的 `#10a37f`
- 输入区与发送按钮属于同一体块
- 生成中止按钮与发送按钮使用同一形制，不换组件语言

## 7. 页面级 PRD

### 7.1 首页 `/`

#### 目标

首页不再只是“会做什么”的说明页，而是“产品已经成熟”的入口页。

#### 信息结构

1. 顶部浮动导航
2. Hero：品牌价值 + 产品预览
3. 可信能力区
4. 工作流区
5. 产品片段 / 截图式预览区
6. 最终 CTA
7. Footer

#### Hero 规格

左侧内容：

- 品牌 badge
- 强叙事标题
- 1 段不超过 3 行的价值说明
- 主 CTA、次 CTA
- 3 个关键指标

右侧内容：

- 必须是产品预览感模块，不是抽象插画
- 预览内容建议模拟：
  - 引用式回答片段
  - 检索结果卡
  - 知识库状态卡
  - 文档结构片段

视觉要求：

- Hero 为大面板，不是纯文本堆叠
- 标题强，但不能像潮流海报
- 产品预览区域必须看起来来自真实控制台

#### 首页模块要求

能力区：

- 最多 3 个能力块
- 每个能力块强调真实业务价值
- 不要使用泛 AI 术语堆砌

工作流区：

- 维持 3 步结构
- 但每一步增加更具体的输入和结果感

产品片段区：

- 必须加入“引用回答”“知识库组织”“结构化 RAG 观测”中的至少两个
- 这是首页最关键的成熟度证明模块

#### 首页验收标准

- 首屏 5 秒内能理解产品不是聊天壳
- 有真实产品预览感
- CTA 清晰
- 不出现模板式 SaaS 三栏卡片堆满全页的廉价感

### 7.2 认证页 `/auth/*`

#### 目标

认证页应与首页和应用壳同属一套品牌，但更聚焦，避免杂讯。

#### 布局

- 保留浮动顶部导航
- 主体区域居中
- 表单容器宽度 `420-480px`
- 背景延续浅绿色氛围光斑

#### 表单容器

- 使用 `Panel Card`
- 标题、描述、表单、辅助链接分层明确
- OAuth、邮箱、密码字段统一节奏

#### 差异化要求

- 登录页强调“返回工作台”
- 注册页强调“创建知识工作台”
- 忘记密码页强调“找回访问权限”

#### 认证页验收标准

- 不能像默认 shadcn 表单页
- 视觉上与首页连续
- 表单易读，重点清晰

### 7.3 工作台 `/dashboard`

#### 目标

Dashboard 必须从欢迎页升级为“当前系统状态总览”。

#### 信息结构

1. 页面标题区
2. 顶部关键行动区
3. KPI 概览区
4. 最近对象 / 最近动作
5. Structured RAG 概览区
6. 快速入口区

#### Header 规格

保留欢迎语，但只占小面积。页面打开后第一屏应先看到系统状态，而不是情绪化文案。

#### KPI 概览

至少包含：

- 知识库总数
- 文档总数
- 最近 24h 索引/问答活动
- 当前配置状态或模型可用状态

显示规则：

- 数值大、标签小
- 每张卡只承载一个核心指标
- 允许 1 张卡强调风险或提醒

#### 最近对象区

建议模块：

- 最近访问知识库
- 最近更新文档
- 待处理上传或处理中对象

如果当前数据不足，可先用结构占位和空态规则保留位置，不要删掉模块概念。

#### Structured RAG 概览

当前仓库已有 `StructuredRagOverview`，应纳入 Dashboard 主信息流，而不是边角附属内容。

#### Dashboard 验收标准

- 打开后先看到“系统正在发生什么”
- 能自然进入下一步操作
- 快捷入口不再是页面主角，状态模块才是主角

### 7.4 聊天页 `/chat`

#### 目标

聊天页必须体现“有来源的知识问答工作台”，而不是聊天软件换皮。

#### 页面结构

1. 顶部工具栏
2. 会话主体区
3. 引用/工具过程展示区
4. 底部输入区

#### 顶部工具栏

必须稳定承载：

- 知识库切换
- 文档范围过滤
- 新建对话
- 上传入口
- 清空会话或保存到知识库

视觉要求：

- 工具栏应成为一块清晰的 surface
- 筛选器和按钮同一高度体系

#### 会话区

消息样式必须区分：

- 用户消息
- AI 回答
- 工具过程
- 引用跳转点

AI 回答卡片应更强调可读性：

- 行宽控制
- 代码块与引用块边界清楚
- 不靠过重边框堆出结构

#### 输入区

输入区浮在页面底部，但不能像独立第三方插件。

实现要求：

- 背景渐隐过渡可保留
- 输入框最大宽度 `768px-880px`
- 发送按钮是品牌强调点
- 停止生成按钮使用相同轮廓语言

#### 聊天页验收标准

- 看起来像知识工作区，而不是普通 IM
- 工具栏、会话、输入区形成同一阅读路径
- 引用与消息层级清晰

### 7.5 知识库列表 `/knowledge-bases`

#### 目标

这是最核心的业务对象页之一，必须体现“组织知识”的秩序感。

#### 页面结构

1. 页面标题与总览统计
2. 搜索 + 创建 + 视图切换 toolbar
3. 结果状态条
4. Grid 或 Table 内容区

#### Grid 视图

知识库卡片统一为 `Object Card`：

- 顶部：标题、描述、操作菜单
- 中部：文档数、chunk 数、更新时间
- 底部：状态标签或快速动作

卡片气质：

- 浅底
- 明确边界
- 轻 hover 提升
- 不允许彩色装饰满屏

#### Table 视图

适用于高密度浏览：

- 表头弱底
- 行 hover 柔和
- 数值列固定宽度

#### Create Card

创建知识库入口允许作为第一张卡，但它必须与真实知识库卡同属一套语言，只是 CTA 更明确。

#### 知识库列表验收标准

- Grid 和 Table 两种视图气质一致
- 搜索、统计、列表三者层次清楚
- 页面有“信息管理系统”感，而不是一堆营销卡片

### 7.6 知识库详情 `/knowledge-bases/:id`

#### 目标

知识库详情页要让用户明确看到某个知识空间的状态与内容。

#### 页面结构

1. 知识库头部摘要
2. 文档工具栏
3. 文档列表 / 网格
4. 上传与设置对话框

#### Header 规格

必须包含：

- 知识库名
- 描述
- 核心指标
- 上传按钮
- 设置入口

建议增加：

- 最近更新时间
- 索引状态提示
- 文档规模分级提示

#### 文档内容区

支持 grid / table 两种形态，但风格统一：

- 文档卡片更像文件对象，不像营销 feature card
- 支持搜索、筛选、上传
- 空态要强调“上传文档开始构建”

#### 知识库详情验收标准

- 页面头部能说明“这个知识库当前是什么状态”
- 内容区更像资产管理，不像内容推荐流

### 7.7 文档详情 `/documents/:id`

#### 目标

文档详情页需要体现“阅读、编辑、版本、AI 重写”四个能力的整合。

#### 布局

桌面端：

- 左：主阅读/编辑区
- 右：信息侧栏 + 版本历史

移动端：

- 主阅读区优先
- 侧栏内容下沉到折叠 section 或顺序堆叠

#### Header

必须承载：

- 返回路径
- 文档标题
- 当前版本
- 阅读/编辑切换
- AI 重写
- 下载

#### 主区

- 阅读模式要像文档阅读器
- 编辑模式要像内容工作区
- 顶部要说明当前模式

#### 侧栏

1. 文档信息
2. 版本时间轴 / 历史列表

版本区应更像时间线，而不是普通列表。

#### 文档详情验收标准

- 阅读和编辑模式切换清晰
- 侧栏信息密度高但不乱
- 版本历史有可追溯感

### 7.8 支撑页统一模板

适用于：

- `/trash`
- `/profile`
- `/sessions`
- `/security`
- `/settings/ai`

#### 模板规则

1. 页面 header 统一包含返回、标题、2 到 3 个状态摘要
2. 主内容为单栏或双栏 `Panel Card` 组合
3. 说明类侧栏使用 `Panel Card`，不要裸文本块
4. 危险操作统一落在页面底部或明确分区中

#### 具体语气

- `Trash`：强调风险和恢复窗口
- `Profile`：强调账号完整性和身份信息
- `Sessions`：强调安全、设备、最近活动
- `Security`：强调保护、变更、验证
- `AI Settings`：强调当前 provider、模型状态、配置完成度

## 8. 响应式规则

### 8.1 Breakpoints

- `375px`
- `768px`
- `1024px`
- `1440px`

### 8.2 规则

- 小屏减少横向并列模块，不减少信息语义
- 大标题可缩，但层级不能消失
- 侧栏在移动端转抽屉
- 双栏详情页在平板以下改为单栏
- 表格在小屏可退化为卡片列表，但不允许横向滚出体验失控

## 9. 动效与交互

### 9.1 总原则

动效只承担反馈，不承担装饰表演。

### 9.2 时长

- hover：`150-200ms`
- panel reveal：`200-260ms`
- dialog / sheet：`220-280ms`

### 9.3 动画限制

- 不做持续漂浮
- 不做无限脉冲
- 不做大面积视差
- 不做卡片 hover scale 引发布局抖动

### 9.4 必备交互反馈

- 所有可点元素有 hover/focus
- 加载有 skeleton 或明确 loading
- 错误有 `role="alert"` 或等效语义
- 危险操作必须二次确认
- `prefers-reduced-motion` 必须生效

## 10. 文案与语气

Groundpath 的文案不应像泛 AI 助手，不应过度热情，也不应技术腔过重。

语气要求：

- 专业
- 克制
- 明确
- 可验证

文案建议：

- 少用“魔法”“智能秒懂”等空泛词
- 多用“来源”“引用”“结构”“上下文”“版本”“范围”这类真实产品词汇

## 12. 建议实施顺序

必须按以下顺序推进：

1. Token 与基础组件
2. 应用壳与导航
3. 聊天输入区与共用 toolbar
4. Dashboard
5. 首页与认证页
6. 知识库列表与详情
7. 文档详情
8. 支撑页统一模板

原因：

- 越靠前越像基础设施
- 越靠后越依赖前面的视觉基线
- 倒序实施会导致大量返工

## 13. 验收清单

- 首页、认证页、工作台、聊天页、知识库页明显属于同一产品
- 品牌绿只出现在高价值位置，没有泛滥
- 登录后页面默认不再长成灰白模板
- Dashboard 有真实工作台感，而非欢迎页感
- Chat 看起来像知识问答工作区，而非 IM
- 知识库和文档对象拥有统一对象语言
- 支撑页不再是随机拼装的表单页面
- 浅色和深色模式都具备清晰对比
- 移动端没有横向滚动和被固定元素遮挡的问题
- 所有关键交互具备 hover、focus、loading、error 反馈
